# fixture-prisma-guide

LLM이 다른 LLM에게 넘기는 설계 문서다. Web(Playwright) 쪽에서 User와 합의한 내용을 적는다. 나중에 Flutter App 쪽 테스트를 만드는 LLM이 같은 규칙을 따르도록 하기 위한 문서다.

- 작성: 2026-11-22
- 근거: User와 한 질문, 답 세션 (결정마다 User가 선택했다)
- 이 저장소는 공개 저장소다. 이 문서에 비밀번호, 접속 주소, 키를 쓰지 않는다.

## 0. 이 문서를 읽는 LLM에게

- User와는 한국어로, 짧고 평이한 문장(ASD-STE100 스타일)으로 이야기한다. 저장소 루트의 `LLMS.md` Rules를 먼저 읽는다.
- 결정할 일은 하나씩 묻는다. 선택지를 주고, 추천안을 맨 앞에 둔다. 번호 목록으로 여러 쟁점을 한꺼번에 던지지 않는다.
- 이모지를 쓰지 않는다.
- 아래 "결정"은 User가 고른 것이다. 바꾸려면 먼저 User에게 묻는다.
- "구현 상태"를 확인한다. 아직 없는 서버 API를 있다고 가정하지 않는다.

## 1. 목적

- Web 테스트와 App 테스트가 **같은 실행 번호에서 같은 난수(Fixture)** 를 쓴다. 그래서 두 플랫폼의 결과를 같은 조건에서 비교할 수 있다.
- 모든 테스트 코드의 성공/실패를 DB에 쌓는다. 나중에 Grafana로 실패율을 본다.
- 실행 번호마다 Web과 App이 모두 실행했는지 DB에서 셀 수 있다.

## 2. 용어

| 용어 | 뜻 |
|---|---|
| 실행 번호 (run_no) | Web과 App이 함께 쓰는 하나의 번호 줄. 1, 2, 3... **전체 실행 한 번에 번호 하나**다. 테스트 파일마다 따로 세지 않는다. |
| 플랫폼 | `web` 또는 `app` |
| Fixture | 실행 번호별 난수 값. 서버가 만들고 DB에 저장한다. |
| 이름표 (test_case) | 테스트를 가리키는 짧은 이름. 예: `deposit`. Web과 App이 같은 테스트에 같은 이름표를 쓴다. 파일 이름과는 따로다. |
| Blocked | 무효가 된 번호. 기록은 남지만 통계에서 뺀다. |
| 코드 종류 (kind) | `spec`(테스트 본문), `common`(재사용 업무 동작), `api`(API 검증 도구), `fixture`(테스트에 쓰는 값을 만들거나 받아 오는 코드, 번호와 기록을 다루는 코드) |

## 3. 결정 사항

### 3.1 DB 위치
- PostgreSQL의 별도 스키마 `testschema`에 둔다. 앱 테이블은 `public` 스키마에 있다.
- 앱 DB 초기화(`/api/testData/reset`)는 앱 테이블 이름을 하나씩 적어서 비우므로 `testschema`는 지워지지 않는다.

### 3.2 번호 규칙
- 실행을 시작하면 서버에 "플랫폼 X가 시작한다"고 알린다.
- 서버는 가장 최신 번호를 본다.
  - 그 번호가 `open`이고 X가 아직 그 번호를 실행하지 않았으면, X는 **그 번호에 합류**하고 같은 Fixture를 쓴다.
  - X가 이미 그 번호를 실행했거나 그 번호가 `blocked`이면, 서버가 **새 번호(최신+1)** 와 새 Fixture를 만든다.
- 최신보다 예전 번호는 닫힌다. 다시 돌리지 않는다.
- 예: Web이 217까지 했고 App이 218, 219를 했다. Web의 다음 실행은 218이 아니라 219다.
- 두 플랫폼이 거의 같은 순간에 "새 번호가 필요하다"고 판단해도 새 번호는 하나만 생긴다(서버 잠금 + DB 고유 조건). 늦은 쪽은 그 번호에 합류한다.

### 3.3 동시 시작
- Web과 App이 같은 번호를 동시에 돌리려 하면 **나중 쪽이 기다린다**(상태 `waiting`).
- 기다린 쪽도 **같은 번호, 같은 Fixture**를 쓴다. 번호는 바뀌지 않는다. 기다리는 이유는 같은 값(같은 아이디 등)을 쓰는 두 실행이 데이터를 서로 건드리지 않게 하려는 것이다.
- 기다리는 사이에 앞선 실행이 Blocked가 되면, 기다리던 쪽은 그 번호를 돌리지 않고 새 번호를 받는다.

### 3.4 완료와 Blocked
- 실행이 끝까지 돌면 그 플랫폼은 그 번호를 "했다"(`finished`). 각 테스트의 성공/실패는 그대로 기록한다. 실패도 정상적인 결과다.
- 어느 한 플랫폼이라도 **중간에 멈추면 그 번호 전체가 Blocked**다. 다른 플랫폼이 이미 끝까지 돌았어도 마찬가지다. 기록은 남기고 통계에서 뺀다.
- "중단"이라는 상태를 따로 두지 않는다. Blocked 하나로 처리한다.
- 멈춤은 두 가지로 알아낸다.
  - 테스트 도구가 멈춤을 알 수 있으면(예: Ctrl+C) 그 자리에서 Blocked를 보낸다.
  - 프로세스가 신호 없이 죽으면, **마지막 신호 뒤 10분**이 지났을 때 서버가 Blocked로 바꾼다.
- 그래서 실행 중에는 신호를 계속 보내야 한다. **테스트 하나가 끝날 때마다 결과를 보내면 그것이 신호가 된다.** App은 테스트를 차례대로 돌려서 실행이 길어지므로 이 점이 특히 중요하다.

### 3.5 기록 실패
- 실행 도중 결과를 서버에 보내지 못해도 테스트는 계속한다.
- 못 보낸 기록은 로컬 파일에 잠시 모아 두고, 실행이 끝날 때 다시 보낸다.
- 그래도 못 보내면 그 번호는 Blocked가 된다(기록이 빠진 결과는 믿을 수 없다).
- 시작할 때 번호와 Fixture를 받지 못하면 테스트를 시작하지 않는다.

### 3.6 일부 실행
- 전체가 아니라 일부 테스트만 돌리는 실행(예: 입금 테스트 하나)은 **번호를 받지 않고, DB에 올리지 않고, 통계에 넣지 않는다.**
- 이것은 개별 테스트 코드의 점검이다. 성공/실패는 로컬 로그로만 남긴다.

### 3.7 Fixture
- 서버(API)가 한곳에서 만든다. 클라이언트(TypeScript, Dart)는 난수를 만들지 않고 받아서 쓴다. 그래서 난수 규칙을 두 언어로 따로 쓰지 않는다.
- 키는 **번호 / 이름표 / 항목**이다. 예: `217 / deposit / amount`.
  - Web의 입금 테스트와 App의 입금 테스트는 같은 값을 받는다.
  - 입금 테스트와 계좌 테스트는 다른 값을 받는다. 그래서 병렬로 돌아도 서로 부딪히지 않는다.
- 항목은 칸이 아니라 줄로 저장한다. 새 테스트가 새 항목을 필요로 해도 DB 구조를 바꾸지 않는다.
- 만드는 규칙은 서버의 목록 하나에 둔다(이름표별 항목과 규칙). 이 목록이 Web과 App 사이의 약속이다. 새 테스트를 만들 때 필요한 항목을 이 목록에 더한다(User가 고른 "필요할 때 더하는" 방식).
- 이미 열린 번호에 없는 항목을 요청하면, 서버가 그때 만들어 저장한다. 뒤에 오는 플랫폼도 같은 값을 받는다.
- 목록에 없는 항목을 요청하면 서버는 분명한 오류를 낸다.

### 3.8 테스트 독립
- 테스트끼리는 **값만 공유하고 데이터는 독립**이다. 각 테스트는 Fixture에서 자기 몫의 값을 꺼내 자기 데이터(계정, 계좌)를 스스로 만든다. 다른 테스트가 만든 데이터를 이어서 쓰지 않는다.
- 각 테스트는 시작과 끝에 자기 데이터를 지운다. Web의 하드 삭제 API는 로그인한 사용자 자기 데이터만 지운다.
- Web은 병렬로, App은 차례대로(1 -> 2 -> 3) 돌린다. 테스트가 독립이므로 순서가 달라도 결과를 이름표로 비교할 수 있다.

### 3.9 실행 환경
- Web 정식 실행은 당분간 **Chrome 하나**로 한다(firefox, mobile-chrome은 쓰지 않는다). Chrome 안에서는 병렬이다.
- 웹 하단의 시연 플레이어는 병렬이 아니라 차례대로 보여 준다.

### 3.10 공개 웹 (EC2)
- 시연 플레이어는 **최신 번호의 Fixture를 읽기만** 한다(화면에 "217번 Fixture"처럼 보인다). 번호를 올리거나 결과를 기록하지 않는다.
- 번호를 열고 결과를 기록하는 쓰기 API는 공개 웹에서 닫는다. 아무나 번호를 올리거나 Blocked로 만들지 못하게 하기 위해서다.

### 3.11 기록 방식
- Web: Playwright에 원래 있는 Reporter 기능을 쓴다(외부 서비스가 아니다). 공통/API/fixture 함수는 이름 붙은 단계(`test.step`)로 감싸고, Reporter가 단계의 시작, 끝, 성공/실패, 걸린 시간을 서버에 보낸다.
- App: 같은 역할의 기록기를 Dart로 따로 만든다. 같은 서버 API를 쓰고, 같은 이름표와 같은 종류(kind) 값을 쓴다.

### 3.12 Web 쪽 파일 배치
- 기존 spec 파일 이름(`000-auth.spec.ts` 등)은 바꾸지 않는다. 각 테스트에 이름표를 붙인다(예: Playwright tag `@deposit`).
- `tests/e2e/fixture/`: 테스트에 쓰는 값을 만드는 코드와, 번호, Fixture, 기록을 다루는 클라이언트 코드. 지금은 무작위 값 도구(`random.ts`, `random-user.ts`, `random-bank-account.ts`)가 있다. Fixture가 들어오면 이 무작위 값은 서버에서 받는 값으로 바뀐다.
- `tests/e2e/starter.spec.ts`: 맨 먼저 한 번 도는 준비 테스트(Playwright setup project). 번호를 열거나 합류하고 Fixture를 받고, 필요하면 기다린다. DB 기능이 맞게 동작하는지도 함께 점검한다. starter가 실패하면 나머지 테스트는 돌지 않는다.

## 4. 테이블 (testschema)

Prisma 설계 파일: `apps/api/prisma/schema.prisma`. DB 변경 파일: `apps/api/prisma/migrations/20261122000000_add_testschema/migration.sql`, `20261123000000_rename_codekind_util_to_fixture/migration.sql`(종류 값 util을 fixture로 바꿈).

### test_run: 실행 번호
| 칸 | 형 | 뜻 |
|---|---|---|
| run_no | serial, PK | 실행 번호 |
| status | `open` / `blocked` | 쓸 수 있음 / 무효 |
| opened_by | `web` / `app` | 이 번호를 처음 연 쪽 |
| created_at | timestamp | 연 시각 |

### test_fixture: 난수 값
| 칸 | 형 | 뜻 |
|---|---|---|
| run_no | int, FK -> test_run | 실행 번호 |
| test_case | text | 이름표 |
| item | text | 항목 이름 |
| value | text | 값. 숫자도 글자로 저장하고 꺼낼 때 바꾼다 |
| created_at | timestamp | 만든 시각 |

PK는 (run_no, test_case, item)이다. 같은 키로 값이 두 개 생기지 않는다.

### platform_run: 번호별 플랫폼 실행
| 칸 | 형 | 뜻 |
|---|---|---|
| id | serial, PK | |
| run_no | int, FK -> test_run | |
| platform | `web` / `app` | |
| status | `waiting` / `running` / `finished` / `blocked` | |
| device | text, 빈칸 가능 | 예: `chrome`, Android 기기 이름 |
| started_at | timestamp | |
| last_signal_at | timestamp | 마지막 신호 시각. 10분 규칙에 쓴다 |
| finished_at | timestamp, 빈칸 가능 | |

(run_no, platform)은 고유하다. "이 플랫폼이 이 번호를 이미 했다"를 DB가 보장한다.

### code_result: 코드 결과
| 칸 | 형 | 뜻 |
|---|---|---|
| id | serial, PK | |
| run_no | int, FK -> test_run | Grafana가 번호로 바로 묶어 셀 수 있게 둔다 |
| platform_run_id | int, FK -> platform_run | |
| kind | `spec` / `common` / `api` / `fixture` | |
| test_case | text | 이름표 |
| name | text | 테스트 제목 또는 함수 이름 (예: `createBankAccount`) |
| file | text | 파일 이름 |
| parent_id | int, FK -> code_result, 빈칸 가능 | 이 코드를 부른 spec 결과. spec 자체는 빈칸 |
| status | `passed` / `failed` / `skipped` | |
| attempt | int, 기본 1 | 재시도 번호 |
| error_message | text, 빈칸 가능 | |
| started_at | timestamp | |
| duration_ms | int | |

색인: (run_no, kind), (test_case).

집계 뷰("Web과 App이 모두 끝낸 번호" 등)는 아직 없다. 실제 데이터가 쌓인 뒤 Grafana를 붙일 때 만든다.

## 5. 구현 상태 (2026-11-22)

| 항목 | 상태 |
|---|---|
| testschema 테이블 4개, 상태 값 목록 5개 | 만듦. 로컬 개발 DB에 적용하고 규칙을 시험함 |
| EC2 서버 DB에 적용 | 안 함 |
| 서버 API (번호 열기/합류, Fixture 주기, 신호, 결과 기록, 10분 규칙, 읽기 전용 최신 Fixture) | 안 함. 만드는 방법을 User에게 묻고 진행할 예정 |
| Fixture 규칙 목록 (서버) | 안 함 |
| `tests/e2e/fixture/` | 폴더와 무작위 값 도구만 있음 (common, spec에서 옮김). 번호, Fixture, 기록 코드는 안 함 |
| `starter.spec.ts`, Playwright Reporter | 안 함 |
| 기존 spec에 이름표 붙이기, 난수를 Fixture로 바꾸기 | 안 함 |
| Chrome 하나로 정식 실행하도록 Playwright 설정 변경 | 안 함 |
| App(Flutter) 쪽 기록기와 테스트 | 안 함 |

서버 API의 주소와 요청 형식은 아직 정하지 않았다. App 쪽 LLM은 이 문서를 근거로 API를 추측해서 만들지 말고, 저장소의 현재 코드(`apps/api/src`)를 확인하거나 User에게 묻는다.

## 6. App(Flutter) 쪽이 지켜야 할 것

- 실행을 시작할 때 서버에서 번호와 Fixture를 받는다. Dart 코드 안에서 난수를 만들지 않는다.
- Web과 같은 테스트에는 같은 이름표를 쓴다. 이름표 목록은 서버의 Fixture 규칙 목록과 같다.
- 테스트는 차례대로 돌리되, 각 테스트는 자기 데이터를 스스로 만들고 지운다(독립).
- 테스트 하나가 끝날 때마다 결과를 보낸다(신호를 겸한다). 10분 넘게 신호가 없으면 번호가 Blocked가 된다.
- 결과의 kind 값은 `spec` / `common` / `api` / `fixture` 넷 중 하나다. App 코드도 이 네 종류에 맞춰 나눈다.
- 서버가 `waiting`을 알려 주면 기다린다. 기다린 뒤에도 같은 번호와 같은 Fixture를 쓴다.
- 일부 테스트만 돌릴 때는 번호를 받지 않고 결과를 DB에 올리지 않는다.
- 중간에 멈추면 그 번호는 Web 결과까지 포함해 Blocked가 된다. 사람이 멈출 때는 가능하면 Blocked 신호를 보내고 끝낸다.

## 7. 남은 결정

- 서버 API의 형식과 보호 방법 (공개 웹에서 쓰기를 닫는 구체적인 방법)
- Grafana 접속 계정 (읽기 전용 DB 사용자)
- Fixture 규칙이 바뀌었을 때 지난 번호의 값을 어떻게 다룰지 (예: 규칙 버전 칸)
- EC2 서버 DB에 적용하는 시점
